5. Uploading a file that later becomes CGI
This is another edge case that becomes apparent only when we consider the entire configuration.

Imagine two server blocks.
server {
    listen 8080;

    location /cgi-bin {
        methods GET POST;
        root www;
        cgi_ext .py /usr/bin/python3;
    }
}

server {
    listen 8081;

    location /cgi-bin {
        methods POST;
        root www;
        upload_enable on;
        upload_store www;
    }
}


Both servers access the same physical filesystem.

Your current code allows the second server to create a file in a directory that the first server treats as executable CGI resources.
Server 8081
    │
    ├── Normal POST upload
    │
    └── www/cgi-bin/uploaded.py
                   │
                   ▼
Server 8080
    │
    ├── GET /cgi-bin/uploaded.py
    │
    └── CGI execution branch


Actual test
I reproduced the upload and subsequent CGI dispatch using two server configurations.

The uploaded script was not executed because your CGI function is still empty, but the request correctly entered the CGI branch.
Why this matters
Once CGI execution is implemented, writable upload directories must not accidentally become executable script directories.

Checking only the current location isn't enough because:
- Different locations can share filesystem directories.
- Different servers can share roots.
- _uploadStore can differ from _root.
- A script can be accessible through another route.
Recommendation
For your evaluation configuration, keep these directories separate:
www/
├── static/
├── uploads/       ← Writable uploads
├── cgi-bin/       ← Trusted CGI scripts
└── errors/


Do not allow uncontrolled uploads into CGI execution directories.

This is primarily a configuration and deployment policy, but it's something you must keep in mind when implementing CGI.

The most significant findings from this audit are:
- Index selection can expose a CGI script's source code.
- A separate upload route can place files into another route's CGI execution directory.
- POST can advertise a URL identifying an unrelated resource.
- Unescaped filenames and decoded redirect targets are unsafe.
- Your filesystem safety checks have confirmed race-condition limitations.
- Your response descriptors need an inheritance policy before CGI.
